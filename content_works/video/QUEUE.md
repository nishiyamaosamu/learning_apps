# 学習動画 制作キュー（進捗台帳）

**このファイルが動画制作の唯一の進捗記録**。セッションをまたいでも、文脈が圧縮されても、
ここを読めば「次に何を作るか」「どこまで進んだか」が完全に復元できる状態を保つ。

- **発注側**（次に何を作るか決めて出す）: `video-queue` スキル
- **制作側**（受注した1本を作る）: `create-learning-video` スキル（工程0が受注、工程9が還流）

## 状態

| 状態 | 意味 | 次にやること |
|---|---|---|
| ⬜ `todo` | 未着手 | ここから受注する |
| 🔨 `wip` | 制作中／中断中 | メモの再開地点から続ける（メモが無ければ成果物から判定） |
| 👀 `review` | レンダリング済み・人のレビュー待ち | 人がmp4を見る |
| ↩️ `rework` | 人が見て差し戻した（メモに指摘） | 指摘を直し、**指摘をスキルへ還流する** |
| ✅ `done` | 承認済み・**アプリへ公開済み** | なし |
| ⏸️ `hold` | 保留（要相談・依存待ち） | メモの論点を解消する |

遷移は ⬜ `todo` → 🔨 `wip` → 👀 `review` → ✅ `done`。
差し戻しは 👀 `review` → ↩️ `rework` → 🔨 `wip` → 👀 `review`。
**✅ `done` に上げるのも ↩️ `rework` に落とすのも人**（エージェントは自分で承認しない）。
✅ `done` は手で書かず、**公開コマンド（`scripts/publish.mjs`）が書く**（下の運用ルール8）。

**表の状態セルは必ず絵文字つきで書く**（例 `🔨 wip`）。一覧をスクロールしたときに
状態が色の塊で見えることが目的なので、絵文字を落とすと台帳の意味が薄れる。

## 運用ルール

1. **受注の優先順位**は `rework` → `wip` → `todo`。
   直し（`rework`）と中断の引き継ぎ（`wip`）を、新規制作より先に片づける
   — **放置された `wip` は誰も拾わないまま永久に残る**のがこの方式の弱点なので、先に潰す。
   `todo` は原則 L番号の小さい順。ただし **★（用語の主担当レッスン）は、それを参照する側より
   先に作る**（定義の揺れを防ぐ。対応は LESSON_PLAN の「用語の主担当」節）。
2. **受注したら発注書を読む**: `content_works/<app>/orders/<L番号>.md` にその回の範囲
   （扱う／扱わない）が確定している。無ければ LESSON_PLAN とシラバスから自分で切る
   （発注書の作り方は `content_works/ipa_sg/orders/README.md`。章単位でまとめて起こす）。
3. **着手したら即** その行を `wip` にし、動画IDを埋める（他のエージェントとの二重着手を防ぐ）。
   台帳の更新は**その行だけを差し替える編集**で行う（ファイル全体の書き戻しは、
   並列で動いている他のエージェントの更新を消す）。
4. **中断・失敗したら** `wip` のままメモに再開地点を書く（例:「音声生成まで完了・実装未着手」）。
   状態を戻さない。何もメモを残さずに終わらないこと。
   メモが無い `wip`（クラッシュ・文脈切れ）は、ディスクの成果物から進捗を判定して再開する
   （判定表は SKILL.md 工程0）。
5. **レンダリング完了で** `review` にし、成果物ファイル名と尺を埋める。
   **`done` は人が付ける**（エージェントが自分で承認しない）。
   人が直しを求めるときは `rework` にし、**メモに指摘を書く**（次に拾うエージェントは
   メモしか見ない。会話に書いた指摘は伝わらない）。
6. **1本 = 1エージェント（使い捨て文脈）**。並列で走らせるときは、受注時の `wip` 書き込みを
   必ず先に行う。`src/videos/index.ts` は `scripts/sync-index.mjs` の自動生成なので手で編集しない
   （各自が `<app>/<id>.tsx` を置いて sync を走らせるだけ。何度実行しても結果は同じ）。
   レンダリングはCPUを食うので直列で回す。
7. 状態が `todo` 以外の行を書き換えるときも、**表以外の場所に長文を書かない**。
   詳細は `narration/<app>/<id>.md`（シナリオ）に残す。
8. **人が「review ok」と言ったら公開する**。`draft/` はあくまで**まだ人が見ていないものの置き場**
   なので、承認された回はアプリの完成品置き場（`apps/<app>/contents/videos/`）へ**移す**。
   手でコピーせず、**このコマンドだけで完結させる**（mp4のコピー・`base.json` への登録・
   この台帳を ✅ done にする・**draft から消す**、まで揃う。何度実行しても結果は同じ）:

   ```bash
   cd content_works/video
   node scripts/publish.mjs sg-L1          # 複数まとめてもよい（sg-L1 sg-L2）
   node scripts/publish.mjs --prune        # 昔に公開した回の draft が残っていたら掃除
   ```

   アプリ側の動画ID = **L番号**（`L1` → `contents/videos/L1.mp4`）。視聴進捗のキーなので
   後から変えない。章は上の `### 第N章 …` 見出しから採る（見出しが無い ipa_ip は
   `--chapter <id>:<タイトル>` で明示）。公開したmp4はgit対象外で、追うのは `base.json` の登録だけ。

   公開すると、その回の draft は**公開した版もそれ以前の版（`-v1`…）もまとめて削除される**
   （残しておくと次にレビューするものが埋もれる。1本20MBが積み上がるのも避ける）。
   **✅ done の行の「成果物(draft)」欄は、どの版を公開したかの記録**であってファイルはもう無い
   — 見直したいときは `apps/<app>/contents/videos/L<番号>.mp4` を開く。
   例外的に手元へ残したいときだけ `--keep-draft` を付ける。

> 初期状態（このファイルの作成時点）は、ディスク上の成果物から機械的に判定した。
> **すでに承認済みのものは手で `done` に上げること。**
