## 用語の呼称（以降の回はここに揃える）

| 語 | この回での定義（読み上げ文そのまま） |
|---|---|
| CVSS（共通脆弱性評価システム） | 脆弱性の深刻さを0から10までの点数で表す共通の物差し |
| 基本評価基準 | 脆弱性そのものの性質を点数にする |
| 現状評価基準 | 攻撃の出回り具合や対策の有無で変わる |
| 環境評価基準 | 自分の会社での影響の大きさを加える |
| 脆弱性診断 | ツールや専門家が既知の弱点を網羅的に洗い出す（＝健康診断） |
| ペネトレーションテスト | 実際に侵入を試み、目的を達成できてしまうのかを確かめる（＝実地試験） |
| ホワイトボックス検査 | 設計や仕組みを知らせて調べる |
| ブラックボックス検査 | 内部を知らせず、外から見える情報だけで調べる（＝攻撃者と同じ条件） |
| ファジング | 想定していないデータを大量に送り込み、異常な動きが出ないかを見る |

「脆弱性」の定義は L2（`sg-L2-asset-threat-vuln.md`）の「その脅威につけこまれる、資産側の弱点」に揃え、
この回では定義に戻らず「弱点」という言い方で受けている。

## 範囲の切り分けメモ（発注書の「扱わない」）

- 脆弱性が見つかった後の管理（パッチ適用・SBOM）は L37 → 「見つける・測る」までで止める
- レッドチーム演習は L34。**語は出さず**、s07-5 の「人や組織の動きまで試す訓練は、次回のテーマ」
  という一言だけでペネトレーションテストとの違いを渡す
- エシカルハッカー（L30）・JVN・早期警戒パートナーシップ（L31）は名前も出さない
- CVSS の各評価基準の下位項目（攻撃元区分・攻撃条件の複雑さ等）には踏み込まない
  （試験で問われるのは「三つの基準がある／時間と場所で点が変わる」まで）
- 深刻度のランク分け（緊急・重要…）は出さず、0〜10 の点数と「基本→現状→環境」の関係だけにした

## ページ別の原稿

### P1 title
ナレーションなし（オープニングジングル）。
`series: 情報セキュリティマネジメント講座` / `title: 攻撃者より先に\n弱点を測る` /

### P2 intro（導入）
- メッセージ: 対策を打つ前に、攻撃者より先に自分の弱点を見つけて測る
- 形: 左イラスト（`person-auditor-magnifier`）＋右テキスト（テーマ→攻撃者→結論の3段）

1. 今回は、セキュリティ評価について学びます。
2. 対策を打つ前に、まず自分の弱点がどこにあるのかを知る必要があります。
3. 攻撃者は、こちらの弱点を探して突いてきます。
4. だから、攻撃者より先に自分で見つけて、その深刻さを測るのです。

### P3 cvss（CVSS＝共通の物差し）
- メッセージ: 「危ない」では伝わらない。0〜10の点数にするのがCVSS
- 形: 中央にキーワード（チップ＋大きな CVSS ＋正式名称）、その下に 0〜10 の横スケール

1. 弱点が見つかったとき、困るのがその深刻さの伝え方です。
2. 危ないという言葉だけでは、人によって受け取り方が変わります。
3. そこで使われるのが、共通脆弱性評価システム、CVSSです。
4. 脆弱性の深刻さを、0から10までの点数で表す共通の物差しです。

### P4 criteria（三つの評価基準）
- メッセージ: 基本・現状・環境。点数は時間と場所で変わる
- 形: 横帯3段（番号＋名前＋何で決まるか）＋下に結論の一言

1. CVSSの評価には、三つの基準があります。
2. 一つ目は基本評価基準で、脆弱性そのものの性質を点数にします。
3. 二つ目は現状評価基準で、攻撃の出回り具合や対策の有無で変わります。
4. 三つ目は環境評価基準で、自分の会社での影響の大きさを加えます。
5. つまり同じ脆弱性でも、時間と場所で点数は変わるのです。

### P5 case（★抽象→具体：同じ7点台でも自社では何点か）
- メッセージ: 環境評価基準を見る理由は「うちではどうか」が違うから
- 形: 上に基本評価7.5の帯、そこから左右2社のカードへ分岐（上がる／下がる）

1. たとえば、ある製品に基本評価で7点台の脆弱性が見つかったとします。
2. A社は、その製品をインターネットに公開したサーバで使っています。
3. B社は、外につながらない社内の端末で使っているだけです。
4. 同じ7点台でも、A社では危険度が上がり、B社では下がります。
5. これが、環境評価基準まで見る理由です。

### P6 vuln-scan（脆弱性診断）※ transitionIn: wipe-light
- メッセージ: 既知の弱点を網羅的に洗い出す健康診断
- 形: 左テキスト（キーワード見出し）＋右イラスト（`person-auditor-checklist`）

1. では、弱点はどうやって見つけるのでしょうか。
2. 一つ目の方法が、脆弱性診断です。
3. ツールや専門家が、既知の弱点を網羅的に洗い出します。
4. 人でいえば、悪いところを一通り調べる健康診断にあたります。

### P7 pentest（ペネトレーションテスト）
- メッセージ: 弱点を並べるのではなく、そこから目的に到達できるかを試す
- 形: 横一列の到達ストリップ（検査する人 → 弱点 → 目的達成？）＋上にキーワード

1. もう一つが、ペネトレーションテストです。
2. 検査する人が、実際にそのシステムへ侵入を試みます。
3. 目的は、弱点を並べることではありません。
4. その弱点を使えば、本当に目的を達成できてしまうのかを確かめることです。
5. なお、人や組織の動きまで試す訓練は、次回のテーマになります。

### P8 scan-vs-pentest（対比）
- メッセージ: 目的・やり方・たとえの3観点で違いを固定する
- 形: `vs` パターン（左右の観点を揃える）

1. 二つの違いを整理しておきましょう。
2. 脆弱性診断は、弱点を漏れなくリストにするのが役割です。
3. ペネトレーションテストは、その弱点で侵入できるかを実地で試します。

### P9 fuzzing（ファジング）
- メッセージ: 想定外のデータを大量に流し込み、異常な動きを見つける
- 形: 左に想定外データ3種 → 矢印 → 検査対象 → 異常のバッジ

1. 三つ目の方法が、ファジングです。
2. 想定していないデータを大量に送り込み、異常な動きが出ないかを見ます。
3. 作った人が思いつかなかった穴を、機械の力で見つけられます。
4. ネットにつながる機器や、自社で作ったソフトの検査で役に立ちます。

### P10 box-test（ホワイトボックス／ブラックボックス）
- メッセージ: どの検査でも「内部をどこまで知らせるか」を先に決める
- 形: 明るいパネル（ホワイト）と暗いパネル（ブラック）の2枚。地の明暗そのものが意味になる

1. どの検査でも、先に決めておくことがあります。
2. 検査する人に、内部の情報をどこまで知らせるかです。
3. 設計や仕組みを知らせて調べるのが、ホワイトボックス検査です。
4. 内部を知らせず、外から見える情報だけで調べるのがブラックボックス検査です。
5. 外部の攻撃者と同じ条件になるので、現実に近い結果が得られます。
