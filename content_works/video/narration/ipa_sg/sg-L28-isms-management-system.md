  P3 の最後の1文で「要求事項を満たせば認証を受けることもできる」と位置づけだけ渡し、
  制度・審査・認証の範囲などは一言も出さない（発注書の「扱う」欄どおり）
- 内部監査とシステム監査の違いは L70。P8 は「組織の内部で行う点検」までにして、
  監査の種類の分類には入らない
- 監査指摘への改善計画のケース演習は L96（科目B）。P10 は1場面の追体験のみ
- リスクアセスメント・リスク対応の中身は再説明しない（L24・L25 が主担当）。
  P7 は1文ずつの回収にとどめる

## 抽象→具体の設計（s10）

s06〜s09 で PDCA の型と用語を語ったあと、**s10 で1つの場面に落とす**。
題材は「内部監査で、共有フォルダのアクセス権に退職者の権限が残っていた」——
L22 P6 で語った「入退社・異動に合わせて権限を見直す」がそのまま不適合として現れる形にした
（既習の内容が ISMS の点検で拾われる、という繋がりを作るため）。
指摘票の4行（監査対象・発見・判定・是正処置）で、用語（不適合／是正処置）が
場面の中のどの位置に来るのかが見えるようにしている。

## 音声と字幕を分けた箇所（誤読対策）

TTS が英字読みしないよう、**音声用テキスト（jobs.json）だけ仮名書き**にしている。
字幕（`.tsx` の `N()` 第2引数）は英字表記のまま＝意図的な食い違い（sg-L27 の SNS と同じ扱い）。

| 字幕表記 | 音声用テキスト | 対象セグメント |
|---|---|---|
| ISMS | アイエスエムエス | s02-1, s03-1, s04-1, s05-4, s06-1, s14-2, s15-1 |
| PDCA | ピーディーシーエー | s06-3, s12-2, s15-2 |
| Plan | プラン | s07-1 |
| Do | ドゥー | s07-5 |
| Check | チェック | s08-1, s12-3 |
| Act | アクト | s09-1 |
| JIS Q 27001 | ジス キュー にまんななせんいち | s03-4 |

**v2 で 27001 を仮名書きに変更**（人のレビュー指摘）。当初は L22 の「JIS Q 31000」と違って
正しく読まれると判断して英数字のまま渡していたが、生成のたびに桁の切り方が揺れて読みが安定しなかった。
JIS Q の番号は**桁数によらず必ず音声側を仮名書き**にする（L29 の 27002・27014 も同じ扱い）。

**v3 で「JIS Q」まで仮名書きに広げた**（人のレビュー指摘）。v2 は数字だけを仮名にしたので
`JIS Q にまんななせんいち` とラテン文字と仮名が1文に混在し、読みが不自然なままだった。
仮名書きにするときは**読み上げる語のまとまり全体**（規格名なら記号部も含めて）を仮名に揃える。
分かち書き（`ジス キュー にまんななせんいち`）は語の切れ目を作るために入れている。
字幕・画面テキストは数字表記「JIS Q 27001（ISO/IEC 27001）」のまま。

## 原稿（字幕＝読み上げテキスト。1文＝1セグメント＝字幕1枚）

### s02 導入：決めても続かない（custom：左イラスト person-employee-m-worry.png＋右テキスト）
1. 今回は、ISMSと呼ばれる仕組みについて学びます。
2. ルールを決め、リスクに手を打っても、それだけでは長続きしません。
3. 担当者が変わると忘れられ、状況が変わっても見直されません。
4. そこで、守る活動そのものを、組織で回る仕組みにします。

### s03 ISMSは仕組みの規格（custom：左キーワード見出し＋右に2行の対比）
1. ISMSは、情報セキュリティマネジメントシステムの略です。
2. ファイアウォールのような、個々の対策のことではありません。
3. 組織として決め、実行し、点検して直す、その仕組み全体を指します。
4. その要求事項は、JIS Q 27001という規格に定められています。
5. 要求事項を満たせば認証を受けることもできますが、その制度は次回学びます。

### s04 適用範囲（custom：会社の枠＋部門タイル6枚。対象の2枚だけ青）
1. ISMSを作るとき、最初に決めるのが適用範囲です。
2. どの事業や拠点、どの情報を対象にするのかを区切ります。
3. 全社を一斉に対象にしなくてもかまいません。
4. 対象をはっきりさせないと、守るべき範囲があいまいになります。

### s05 リーダーシップ（custom：左テキスト3行＋右イラスト person-leader-point.png）
1. 次に欠かせないのが、経営層のリーダーシップです。
2. 経営層が情報セキュリティ方針を定め、組織の内外に示します。
3. 人や予算といった資源を割り当てるのも、経営層の役割です。
4. 現場任せで経営層が関わらないものは、ISMSとは呼べません。

### s06 ★PDCAの型（custom：2×2の時計回り＋中央に循環バッジ・wipe-lightで章転換）
1. ISMSの中身は、四つの段階を繰り返す形になっています。
2. 計画を立て、運用し、点検して、改善する。
3. 頭文字をとって、PDCAサイクルと呼びます。
4. 一周して終わりではなく、回すたびに良くしていきます。

### s07 計画と運用（custom：上段Pに2カード／下段Dに横長1帯）
1. 最初のPlan、計画の段階を見ましょう。
2. ここで行うのが、すでに学んだリスクアセスメントです。
3. どんなリスクがあるかを洗い出し、大きさを測って順位を付けます。
4. そのうえで、回避や低減といったリスク対応を決めます。
5. 続くDoでは、決めた対応を日常業務として実行していきます。

### s08 パフォーマンス評価（vs：内部監査／マネジメントレビュー・columnAtSec で左右を同期）
1. 三つ目のCheck、パフォーマンス評価です。
2. 決めたとおりに動いているかを、自分たちで点検します。
3. 組織の内部で行うこの点検を、内部監査と呼びます。
4. その結果を経営層が受け取り、仕組み全体を見直します。
5. これを、マネジメントレビューといいます。

### s09 改善（custom：縦3行＋下に継続的改善）
1. 最後のAct、改善の段階です。
2. 点検で見つかった、決めたとおりでない状態を不適合といいます。
3. 目の前の不具合を直すだけでは、また同じことが起こります。
4. 原因までさかのぼって取り除くことを、是正処置と呼びます。
5. これを繰り返して仕組みを良くしていくのが、継続的改善です。

### s10 【抽象→具体】監査の指摘（custom：左イラスト person-auditor-checklist.png＋右に指摘票4行）
1. 具体的な場面で、この流れを追ってみましょう。
2. 内部監査で、共有フォルダのアクセス権が調べられました。
3. すると、退職した社員の権限が残っていることが分かりました。
4. 決めたとおりでないので、これが不適合です。
5. 権限を消すだけでなく、棚卸しの手順を作るところまでが是正処置です。

### s11 クイズ幕間（SectionTitle・共通音声 QUIZ_INTRO_SEG）

2. 内部監査は、PDCAのどの段階にあたるでしょうか。

### s13 クイズ②（是正処置は原因の除去・正解A）

### s15 まとめ（summary・wipeで転換・共通音声 OUTRO_SEG）
1. ISMSは、情報を守る活動を組織で回す仕組みです。
