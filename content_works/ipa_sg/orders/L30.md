# SG-L30 インシデントハンドリングとセキュリティ組織

- **一言で**: 事故が起きたら「気づく→順位を付ける→動く→報告する」— それを担う専門チーム
- **シラバス**: 情報セキュリティ#2「情報セキュリティ管理におけるインシデント管理」全部＋「情報セキュリティ組織・機関」の組織内側（委員会・CSIRT・PSIRT・SOC・エシカルハッカー。外部機関はL31へ）
- **主担当**: ★ インシデント管理（情報セキュリティ側）。L93・L94（科目B）はこの回の用語で統一する。**L68（ITサービスマネジメントのインシデント管理）とは同名の別概念**で、その区別に必ず触れる
- **依存**: なし（L22 が「扱わない」で本回へ送った「情報セキュリティ事象とインシデントの区別・監視の体制」を受ける。**L22 の四つの柱に「監視」は無い**ので柱の回収という書き方はしない。第9章 L93・L94 より先に作る）

## 扱う

| 用語・論点 | 何を語るか |
|---|---|
| 情報セキュリティ事象とインシデント | 「おや？という出来事（事象）」のうち、実害・その恐れがあるものがインシデント。言葉の区別から入る |
| インシデントハンドリングの流れ | 検知/連絡受付→トリアージ→インシデントレスポンス→報告/情報公開。この4ステップが回の背骨 |
| トリアージ | 全部には対応できないので優先順位を付ける。医療現場の言葉の借用、で腹落ちさせる |
| テイクダウン | 偽サイトやC&Cサーバを停止に追い込む対応。レスポンスの具体例として |
| 情報セキュリティ委員会とCSIRT・PSIRT・SOC | 決める組織（委員会）と動く組織（CSIRT）、製品担当（PSIRT）、24時間監視（SOC）の役割分担を地図で |
| エシカルハッカー | 攻撃者の技術で守る側に立つ人。L33（ペネトレーションテスト）への予告 |
| L68との用語の区別 | ITサービスマネジメントの「インシデント管理」は障害対応の話で別概念。第8章で再会する、と明言する |

## 扱わない
- 外部の機関（NISC・IPA・JPCERT/CCなど）→ L31
- インシデント対応規程（文書側）→ L27（参照のみ）
- 被害状況の調査・復旧 → L26（参照のみ）、デジタルフォレンジックス → L40
- マルウェア感染時の初動・偽警告対応のケース演習 → L93、分析・再発防止のケース演習 → L94（科目B）

## 確認パート
- 通常クイズ2〜3問
- 出しどころ: ハンドリング4ステップの並び／トリアージの目的／CSIRTとSOCの役割の違い
