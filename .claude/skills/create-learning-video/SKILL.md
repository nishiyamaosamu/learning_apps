# 学習動画の制作（Remotion / 集中ブルー / ナレーション同期）

この仕事は「型にコンテンツを流し込む」作業ではない。**シナリオ（語り）が背骨で、
各ページはその語りを最もよく伝える絵**だ。1ページずつ、そのページのあるべき姿を
考えてレイアウトを設計する。見応えのある動画は、ページごとに最適な見せ方が選ばれていて、
隣り合うページが同じ形をしていない。

守るべき土台は固定されている:
- **色はトークンだけ**（`src/design/tokens.ts` の colors）。ハードコード禁止
- **動きは `useCurrentFrame`/`interpolate` 系だけ**（`src/parts/animate.ts` のフック）。CSS animation/transition は禁止（レンダリングが壊れる）
- 本編ページは下部に**ナレーション同期字幕**を常設（`SlideShell` に narration を渡せば保証される）
- 文字は大きく・要素は少なく（動画は視聴距離が遠い）
- **尺は1本5分以内が目標。5:59（359秒）まではセーフ、6分以上はアウト**。原稿の文字数で管理する
- **BGM・効果音は入れない。出現アニメが終わった後の微動（脈動・浮遊・ドリフト）も入れない** —
  音や常時動くものは学習の邪魔になるため（2026-07-07 の試作レビューで確定。
  `public/audio/common/bgm.mp3` が残っていても使わない）。演出はナレーション同期の出現
  （`segStart`）とレイアウト設計・ページごとのリズムで作る

作業ディレクトリ: `content_works/video`

アプリ別の名前空間: パス中の `<app>` はレッスンが属するアプリのディレクトリ（`ipa_ip` / `ipa_sg`）。
動画ID `<id>` はアプリ接頭辞つきでグローバル一意にする（ipa_ip → `ip-…`、ipa_sg → `sg-…`。
例 `ip-L1v9-corporate-activity`）。スクリプト類（audio-durations / stills / render）には `<id>` だけ渡せばよい
（接頭辞から `<app>` が決まる）。

**このスキルが制作知識の唯一の記憶**。動画は1本ごとに新しい文脈で作られるため、
過去の会話・セッションの記憶は次の1本に引き継がれない。ここ（SKILL.md と references/）に
書かれていることが、全エージェントが共有できる唯一の基準になる（工程9を参照）。

**始める前に、自分がどちら側かを確かめる。** ユーザーから直接「動画を作って」と頼まれた
メインの担当なら、**自分で作らずに `video-queue` スキルへ回す**（1本ぶんの原稿・コード・静止画を
読むとその文脈は数本で溢れ、後続の動画の品質が落ちる。発注側と制作側を分けるのはそのため）。
すでに「この1本を担当して」と発注されているなら、あなたが制作側。そのまま工程0へ進む。

## ワークフロー

### 0. 受注と台帳（1本の始まりと終わり）

進捗の記録は `content_works/video/QUEUE.md`（進捗台帳）が唯一の正。

**どの回を作るか指示されている場合はそれに従う**（その行を使う）。指示がなければ、
台帳を読んで次の**優先順位**で1本受注する:

1. **`rework` の行**（人のレビューで差し戻された動画）— 直しは新規制作より優先する。
   受注したら工程1〜8で直し、**工程9でその指摘をスキルへ書き戻す**
2. **`wip` の行**（前のエージェントが中断した動画）— 放置すると誰も完成させない
3. **`todo` の行** — 原則 L番号順。ただし★＝用語の主担当は、それを参照する回より先に作る

受注したら**すぐ** その行を `🔨 wip` にし、動画IDを埋めてから制作に入る（二重着手の防止）。
台帳の更新は必ず**その行だけを差し替える編集**で行う（ファイル全体の書き戻しは、
並列で動いている他のエージェントの更新を消す）。
**状態は必ず絵文字つきで書く**（⬜ `todo` / 🔨 `wip` / 👀 `review` / ↩️ `rework` / ✅ `done` /
⏸️ `hold`）。一覧を見たときに状態が塊で見えるための表記なので、絵文字を落とさない。

動画IDは `<接頭辞>-L<レッスン番号>-<英小文字スラッグ>` （例 `sg-L79-asset-register`）。
台帳に載っていない回を作るよう指示されたときは、行を追加してから始める。

**中断した `wip` を引き継ぐとき**は、メモの再開地点を読む。メモが無い／当てにならないときは、
ディスクの成果物から進捗を判定する（クラッシュや文脈切れでメモを書けずに終わった場合）:

| 存在するもの | そこまで完了している | 次にやること |
|---|---|---|
| `narration/<app>/<id>.md` と `.jobs.json` | シナリオ（工程2） | 工程4（音声生成） |
| `public/audio/<app>/<id>/*.mp3` | 音声（工程4） | `audio-durations.mjs` → 工程5 |
| `src/videos/<app>/<id>.audio.json` | 尺の実測 | 工程5（実装） |
| `src/videos/<app>/<id>.tsx` | 実装（工程5） | 工程6〜8（検証・目視・レンダリング） |
| `draft/<app>/<出力名>.mp4` | レンダリング（工程8） | 尺を確認して `👀 review` にする |

`draft/` に居るのは**レビュー待ちの回だけ**。✅ `done` の回は公開時に draft から消えている
（実体は `apps/<app>/contents/videos/L<番号>.mp4`）ので、done 行の成果物が無いのは正常。

**中断・失敗して終わるとき**は、`🔨 wip` のままメモに**再開地点**を書いて終わる
（例:「音声生成まで完了・実装未着手」）。何も書かずに終わらない。
発注元への報告も工程8のフォーマットに揃え、**エラーログや調査の経緯を長々と貼らない**
（何が終わって何が残っているか＋再開地点の1行で足りる）。

レンダリング完了（工程8）で `👀 review` にし、成果物ファイル名と尺を埋める。
**`✅ done` に上げるのも `↩️ rework` に落とすのも人**。自分で承認しない。

### 1. 手本と道具を知る

最初に必ず読む:
- `src/videos/demo/narration-demo.tsx` — ナレーション＋字幕同期の最小手本。**必読**
- `src/videos/demo/demo.tsx` — 全パターンの記述例 + カスタムシーンの手本（StatScene）
- `references/custom-scenes.md`（このスキル内）— カスタムシーンのレシピ集。**必読**
- `references/narration.md`（このスキル内）— 音声パイプラインの詳細（コマンド・命名・部分再生成・トラブルシュート）。
  **工程2でジョブJSONを書く前に読む**（読み分け・セグメント命名の決まりが原稿の書き方に効く）

### 2. シナリオライティング（語りが背骨）

実装より先に「語り」を書き切る。動画の質と尺はここで決まる。

**範囲は自前の知識で決めない**（試験対策なので、出題範囲の外を語らない・隣の回と重複させない）。

**発注書 `content_works/<app>/orders/<L番号>.md` があれば、それがこの回の範囲の正。**
「扱う」に挙がった項目は全部語り、「扱わない」は書かない。シラバスを漁り直す必要はない
（範囲は章単位で切り分け済み。書式は `orders/README.md`）。

**動画をアプリの他機能と連動させない。** 発注書の「扱わない」にある「暗記カードへ委譲」等は
範囲切り分けの**内部記録**であり、動画のナレーション・画面テキストには出さない
（「詳しくは暗記カードで補えます」のような誘導文を書かない）。動画は1本で完結した語りにする —
視聴環境によっては暗記カード機能が存在せず、連動を前提にすると成り立たなくなるため
（sg-L4 で混入が実際に起きた）。扱わない用語に触れたくなったら、誘導せず単に語らない。

**他のレッスン番号（L8・L9 など）を画面テキスト・ナレーションに出さない。** レッスン番号は
カリキュラムの見直しで入れ替わる可能性があり、固定ではない — 番号を出すと、並びが変わった
瞬間に動画が指し示す先を間違える（sg-L46 v1 で画面ラベルに「攻撃（L8・L9）」と出て差し戻された）。
L番号は制作側の**内部記録**（発注書・QUEUE.md・narration/*.md・tsx のコメント）にだけ書く。
「前回は」「次回は」のような並び順に依存した言い方も同じ理由で避け、
「これまで」「別の回で」のように順序に依存しない言い方にする。他の回で扱った話題に触れたい
ときは、番号ではなく**内容の名前**で呼ぶ（例:「SQLインジェクションで見たように」）。

発注書が無い回だけ、自分で範囲を切る:

- `content_works/<app>/LESSON_PLAN.md` の**その回の行** — カバー範囲・シーン数目安・
  【地図＋代表】【計算ワーク】【前提：◯◯】の指定。ここに書かれていない話題は入れない
- `content_works/<app>/syllabus_*.md` — 該当項目の用語（LESSON_PLAN の「カバー範囲」の出どころ）
- 科目B（ipa_sg 第9章）は `content_works/ipa_sg/sg_koukai_mondai.md` の対応出題型
- **前後の回**（LESSON_PLAN の同じ章の行）を見て、隣が扱う話題は書かない

発注書の有無にかかわらず、**台帳や発注書に「Lxの定義を参照」「Lxの後」とある場合は、
その回の `narration/<app>/<Lxのid>.md` を読み、用語の呼称・定義・図の描き方を揃える**。
  （同じ用語が回ごとに違う言い方になるのが、シリーズものでいちばん効く劣化）

1. **構成**: title → 導入（なぜ学ぶか・身近な例）→ 本編 → クイズ導入の幕間 → クイズ2〜3問 → まとめ。
   全体で12〜16ページ（title・幕間・まとめを含めた総ページ数。LESSON_PLAN の
   「シーン数目安 10〜13」は本編＋クイズだけを数えた値で、同じことを言っている）
   - title はオープニングジングル（6.8秒）が自動で鳴る。**title にナレーションは付けない**
   - クイズの前に幕間ページを1枚置いて一拍おく。画面は `parts/SectionTitle.tsx` で
     短い題の文字アニメ（例: 「クイズで確認」）、読み上げは**共通音声を使い回す**
     `QUIZ_INTRO_SEG`（「ここまで学んだことを、クイズ形式で確認していきましょう。」固定文言。
     工程4参照）。この文言をジョブJSONに書いて新規TTS生成しない
   - **クイズ2〜3問は、互いに別のトピックにする**。同じ用語を角度を変えて2問続けない
     （sg-L30 v1 は「受け付けた次はトリアージ」→「トリアージの目的」で差し戻された）。
     本編の柱（手順／組織／言葉の区別 など）から1問ずつ拾うと自然に散る。原稿を書いたら
     問題を並べて「何を問うているか」を一語で言い、同じ語が2回出たら作り直す
   - **クイズの正解は A に固定しない**。2択なので放っておくと全問Aになる。1本の動画で
     A/B を必ず両方使う（2問なら A,B か B,A。3問なら A,B,A / B,A,B など）。
     ナレーションは正解を文言で言うので、選択肢の text を入れ替えるだけでよい
     （`key` は上から "A"/"B" のまま。詳細は references/patterns.md「quiz」）
   - まとめは本編の要点を短く復唱し、最後のセグメントは必ず**共通音声**
     `OUTRO_SEG`（「今回のレッスンはここまでです。お疲れさまでした！」固定文言。工程4参照）で締める。
     この文言をジョブJSONに書いて新規TTS生成しない
   - **まとめは `pattern: "summary"` が標準**（docs/DESIGN.html「まとめ①」、実装は
     `scenes/SummarySlide.tsx`）: `points: { text, checkAtSec }[]`（3行まで）に要点を文のまま書く。
     `checkAtSec` は対応するナレーション文の開始秒（`segStart(SEG, i)`）— 読み上げに同期して
     チェックが1つずつ入る。チェック色は primary600（correct 緑は正誤専用なので使わない）。
     新出用語の習得が主眼の回に限り「キーワード回収」（docs/DESIGN.html「まとめ②」。タイトルカードで
     予告したキーワードを意味つきカードで回収）を `custom` で組んでよい。アイコンを「+」でつなぐ
     旧形式は使わない
   - **まとめの頭にはワイプ**: まとめページの spec に `transitionIn: "wipe"` を付ける
     （太めの角丸ラインが画面を埋めてから抜ける約1.5秒の切り替え）。**まとめ前専用・1動画1回**。
     本編内で話題が大きく変わるページには軽量版 `transitionIn: "wipe-light"`
     （斜めの平行四辺形3枚が流れ抜けるだけ・約1.0秒）を使ってよい（1〜2回まで）。
     クイズ導入の幕間にはどちらも付けない（SectionTitle が主役）
   - **仕組み・手順を説明したら、その直後に「具体的な場面で何がどうなるか」のページを1枚置く**。
     ステップ図（STEP1→STEP2 など）は流れは分かるが、**その仕組みが実際に何に適用されるのかは
     伝わらない**。身近な場面（買い物・社内のやり取りなど）を1つ決め、登場人物と
     「何が」対象になるのかを固有名で見せる — 例: ハイブリッド暗号方式（sg-L15）は
     手順の帯のあとに「ネットショップで、①共通鍵は店の公開鍵で、②カード番号や住所は共通鍵で
     暗号化される」を場面図で追加した（人のレビュー指摘で追加。手順だけでは
     「結局どれが暗号化されるのか」が残らない）。抽象→具体の順で1ページ使う価値がある
   - **科目B（試験のケース問題）のレッスンは、確認パートを「知識クイズ」ではなく「ケース問題」にする**
     （ipa_sg LESSON_PLAN 第9章 L78-L96 が対象。ただし L78 はオリエンテーション回なので従来のクイズで例外）。
     用語の一問一答ではなく、**A社などの状況（＝本文・図表）を提示するシーンを1枚置いてから、
     その状況を参照して判断させる quiz を2〜3問**続ける（例: 与えられた評価値から重要度を出す／
     状況の記述から効く対策を選ぶ）。幕間の題は「ケースで確認」、読み上げは共通音声
     `CASE_INTRO_SEG`（「ここまでを踏まえて、ケース問題で確認していきましょう。」固定文言。工程4参照）を
     `QUIZ_INTRO_SEG` の代わりに渡す。実例は `src/videos/ipa_sg/sg-L79-asset-register.tsx`
2. **キーワードは説明してから先へ進む**: 画面に出す用語（例: ミッション・ビジョン・バリュー、
   グリーンIT、カーボンフットプリント）は、名前を読み上げるだけで流さず、それぞれ一言の定義か
   身近な例を必ず語る。用語の羅列は記憶に残らない。語る時間が足りないなら項目ごと削って
   残りを深く — **網羅より記憶**

   **略語の日本語訳を、その用語が守備する範囲だと思い込まない。** 訳語の一語から連想した
   狭い例だけを説明してしまう事故が起きる — sg-L39 v1 は MDM（モバイル端末管理）を
   「モバイル＝スマホ」と読んで「会社が配ったスマートフォンをまとめて管理する仕組み」と
   限定し、差し戻された（実際の対象は**社外へ持ち出す端末＝スマートフォン・タブレット・
   ノートパソコン**）。試験では対象範囲そのものが問われるので、狭い定義は誤答に直結する。
   用語の定義を書いたら、**その語が対象にするものを口に出して並べ、いちばん広い例が
   入っているか**を確かめる（入らないなら定義文が狭い）。**代表例を1つだけ挙げて
   済ませない** — 例が1つだと視聴者はそれを定義だと受け取る。

   定義を直すときは **呼称表・本編の語り・クイズの正解解説・画面テキスト・イラストを
   まとめて直す**（1か所だけ直すと同じ動画の中で用語の広さが食い違う）。
3. **各ページのナレーション原稿**を書く。話し言葉（〜です・〜ます）で、耳で聞いて自然な文。
   Markdown記号や「・」の読みは書かない。字幕にもそのまま出る文なので、読んでも聞いても通じること
4. **1文 = 1セグメント = 字幕1枚**。1文は25〜45字、1ページ2〜6文。長い文は必ず区切る
   （字幕1枚に収まらない文は、聞いていても長い）
5. **原稿の総文字数で尺を管理する**: 読み上げは約4.5〜5字/秒。目標は **1,200〜1,400字（4〜5分）**。
   1,500字を超えたら音声を作る前に削る — ページごと削るのが効く。作った後に削ると再生成コストがかかる。
   逆に3分を大きく下回るなら、キーワードの説明が浅くないか（工程2の観点で）見直す
6. 成果物を2つ書く:
   - `narration/<app>/<id>.md` — シナリオ（ページ表: メッセージ・レイアウト案・原稿）。後から見返す用
   - `narration/<app>/<id>.jobs.json` — セグメント原稿（`s{ページ2桁}-{通し}.mp3` → 文）。TTSの入力

### 3. ページ設計（原稿を絵にする）

シナリオの各ページについて、次の3つを短くメモに書き出す:

1. **メッセージ**: このページで伝えることを一文で。二文になるならページを分ける
2. **あるべき姿**: 視聴者が最初の0.5秒で何を見るべきか（大きな数字？ 対比？ 循環？ 積み上がる構造？ 放射状の関係？ 1つの単語？）
3. **形**: あるべき姿をそのままレイアウトにする（**custom が基本**）

**画面テキストは原稿の要点だけにする。** 字幕がナレーション全文を語るので、
画面に原稿と同じ文を書くと二重になる。画面側はキーワード・図・関係だけを引き受ける。

**聞き慣れない新出用語は、そのページで一番目立つ要素にする。** 概念を大きな文字にして
用語を小さなグレーの添え字にすると、いちばん覚えてほしい語がページで一番目立たなくなる
（sg-L5 の「ランサムウェア」「踏み台」で指摘が出た）。概念も大事だが、**語と意味が
セットで残ること**が試験対策の目的なので、概念文は用語に従属させる。用語ドン（`term`）は
1動画1〜2回までなので、それ以外のページは **キーワード見出し**
（分類チップ＋大きな用語＋一言の定義。レシピは references/custom-scenes.md）を使う。
強調は**文字の大きさとマーカーだけ**で作り、箱・枠・影で囲わない — 集中ブルーは余白で
見せる設計なので、囲みを足すと「装飾が過剰」になる（sg-L5 v3 で差し戻された）。

**custom が基本、パターンは近道。** 循環図・ハブ&スポーク・ピラミッド・数字ドン・カード比較など、
内容が求める形をゼロから設計するのがこの環境の標準的な使い方だ。既製パターン(下表)は
頻出形の実装済みショートカットで、内容がその形に完全に一致するときだけ使ってよい。
「パターンに収まるよう内容を曲げる」のは本末転倒。

| パターン | 形 |
|---|---|
| `bullets` | 並列な列挙（3点まで） |
| `vs` | 2概念の対比 |
| `flow` | 順序ステップ・サイクル |
| `matrix` | 2軸4象限 |
| `layers` | 階層・積み上げ |
| `graph` | 図と式のペア（座標系は references/patterns.md） |
| `term` | 用語ドン（1動画1〜2回まで。`chip` は分類ラベル＝その語が何の一種か。重要度を主張する語は入れない） |
| `binary` | 桁ごとの計算ステップ |
| `quiz` | 理解確認（問→答の間に考える間を置く。references/narration.md） |
| `summary` | まとめ（ポイント復唱・チェックリスト。1動画1回・最終シーン） |

**リズムの設計**（絵コンテ全体を見て確認する）:
- 同じ形（同じ視覚文法）を2ページ連続させない。循環図の直後に放射図など「線で繋ぐ図」を重ねない
- 密なページの次は疎なページ（数字ドン・用語ドンなど）で息継ぎを作る
- ナレーションが長いページ（4文以上）は、要素を時間差で順に出して「語りに画面がついてくる」感を作る
- **並列項目（bullets／vs／flow）は既定タイミングのままにしない**: 何も指定しないと全項目が
  最初の1〜2秒でほぼ同時に出る／点灯が一定間隔で機械的に切り替わる。ナレーションが項目ごとに
  順番へ話す構成なら、必ず該当文の開始秒に同期させる（工程5の `appearAtSec`／`columnAtSec`／
  `highlightAtSec` 参照）。同期させないと、画面が語りより先行して「もう出ているのにまだ説明中」
  というズレが起きる（BECの3ステップ図で実際に起きた不具合）

**イラストを入れるか考える**（ページ設計の一部として毎回検討する）:

手描き風イラスト（スタイル見本: `docs/SAMPLE_STYLE.png`）には、抽象的で難しい話を
易しく感じさせ、イメージを膨らませる効果がある。各ページの「あるべき姿」を考えるとき、
「これは絵で見せた方が入ってくるか？」を必ず一度問う。

- **向いている**: 情景や人物が絡む話（オフィスの場面・攻撃者と守る人）、抽象概念のメタファー
  （信頼＝握手、責任＝天秤、資源＝集まってくる矢印）、導入や締めで感情に訴えたいページ
- **不要**: 構造図・計算・チャートなど、動画側の SVG／レイアウトで描ける形（それは custom で組む）
- **分量**: 1動画 2〜4枚まで。多用すると1枚の効果が薄れる
- **モノのイラストを1枚だけ置くと、その1枚が定義になる**: 複数のものを対象にする用語の
  ページで具体物を1枚しか置かないと、語りをいくら広く書いても対象が狭く見える
  （sg-L39 の MDM はスマホの絵1枚だったので「スマホの仕組み」に見えた）。
  **代表を2枚並べる**か、対象名のチップを添えて絵を補う（既存部品の組み合わせで足りる）

イラストを使うときの手順:
1. **まず既存部品を探す**: `public/images/<app>/`。スタイルは全プロジェクト共通なので
   **他アプリのフォルダも見てよい**（例: ipa_ip の動画から `images/ipa_sg/icon-shield.png` を
   直接参照してよい。ただし色に意味を持たせているアプリの部品は流用先で違和感がないか確認）。
   同じ概念には必ず同じ絵を使い回す（記憶のフック）。
   **流用する前に、その画像を Read で開いて中身を見る。** ファイル名が合っていても、
   絵の中に**文字（ラベル・表題）が描き込まれている**部品は別の概念に流用できない —
   画面に出た瞬間、その文字が「このページは何の話か」を上書きしてしまう
   （sg-L54 は「経理の書類」の絵に `prop-ledger` を流用したが、絵の中に「情報資産台帳」と
   書かれていて差し戻された）。文字入りの部品は、その文字どおりの概念のページでだけ使い、
   合わなければ文字なしの部品を探すか新規生成する
2. 無ければ **create-video-illust スキルを Skill ツールで呼んで生成する**（1枚数分・必ず直列)。
   `<app>` はレッスンが属するアプリ（例: ipa_ip）。制作フロー内からの呼び出しなので
   生成先は `public/images/<app>/` 直下（draft を経由しない — 動画レビューが承認を兼ねる）。
   透過処理まで済ませる。
   codex はフォアグラウンドで実行し、**「バックグラウンドの完了待ち」を理由に作業を止めない**
   （待ち時間には他ページの実装・lint・stills を進める）。イラストが揃わないときは
   該当ページをイラストなし設計に切り替えて完成を優先する
3. シーンでは `<Img src={staticFile("images/<app>/xxx.png")} style={{ mixBlendMode: "multiply", ... }} />`
   で白地を背景に溶かす（references/custom-scenes.md の左右分割レシピ参照）

### 4. 音声生成（実装の前に済ませる）

詳細・部分再生成・トラブルは `references/narration.md`。基本の流れ:

```bash
cd content_works/scripts
mise exec -- uv run tts.py --jobs ../video/narration/<app>/<id>.jobs.json \
    --out-dir ../video/public/audio/<app>/<id>

cd ../video
node scripts/audio-durations.mjs <id>   # 実測秒数 → src/videos/<app>/<id>.audio.json
```

- audio-durations が合計秒数を報告する。**警告（330秒超）が出たらここで原稿を削る** —
  実装後に削るより圧倒的に安い
- 実装は `<id>.audio.json` を import するので、音声を先に作らないと型チェックが通らない（意図的な順序強制）
- **クイズ導入・締めの一言は共通音声（毎回生成しない）**: 文言が固定の定型セリフは
  `public/audio/common/` に一度だけ生成済み。ジョブJSONには**書かず**、
  `src/parts/common-narration.ts` の `QUIZ_INTRO_SEG` /（科目Bのケース確認は `CASE_INTRO_SEG`）/
  `OUTRO_SEG` を import して使う（工程5参照）。新しい定型セリフを追加したいときだけ
  `narration/common/common.jobs.json` に足して `tts.py` → `node scripts/audio-durations.mjs common` を実行し、
  `common-narration.ts` に export を足す

### 5. 実装

`src/videos/<app>/<id>.tsx` を作り、`node scripts/sync-index.mjs` で登録する
（**`src/videos/index.ts` は自動生成なので直接編集しない** — 手で書くと、別の動画を作っている
エージェントとの唯一の衝突点になる。ファイルを置くだけでよい）。
ナレーションの組み立ては `narration-demo.tsx` の形をなぞる:

- `narrationLoader(durations, "audio/<app>/<id>")` で `N()` を作り、セグメント配列を組む
- **クイズ導入の幕間・まとめの締め**は音声を新規生成せず、
  `import { QUIZ_INTRO_SEG, OUTRO_SEG } from "../../parts/common-narration"` で共通セグメントを使う。
  幕間シーンには `narration: QUIZ_INTRO_SEG` をそのまま渡し、まとめのセグメント配列は
  末尾に `OUTRO_SEG` を足す（`[...own, OUTRO_SEG]`）。どちらも `NarrationSegment`（`N()` の戻り値と同じ形）
  なので他のセグメントと混在させてよい。**科目Bのケース確認回は `QUIZ_INTRO_SEG` の代わりに
  `CASE_INTRO_SEG` を使い、幕間の直後にケース提示シーン（本文・図表）を1枚置いてから quiz を続ける**
  （工程2の構成参照。実例 `src/videos/ipa_sg/sg-L79-asset-register.tsx`）
- **既製パターン**: spec に `narration: [...]` を書くだけ（telop は書かない）
- **カスタム**: セグメント配列を定数にして **spec と SlideShell の両方に同じものを渡す**
  （spec 側が音声と尺、SlideShell 側が字幕。片方だけだと音か字幕が欠ける）
- custom の `durationSec` はアニメーションの最低尺。ナレーションの方が長ければ自動で伸びる
- 音声はレンダラーが自動で鳴らす。シーン内に `<Audio>` を手動で置かない（二重再生）
- title はジングルが自動で鳴る（ナレーションなし）。ダーク幕間は中央の大きな文字を読み上げ文と一致させる
- クイズは正解セグメントに `gapBeforeSec: 1.5〜2` を付けて考える間を作り、
  `revealAtSec: segStart(QSEG, i)`（正解セグメントの開始秒。parts/narration.tsx のヘルパー）に合わせる
- 「N文目に合わせて要素を出す」も同じく `useAppear(segStart(SEG, i))` —
  語りに画面がついてくる演出は手計算せずこれで組む
- **bullets／vs／flow は項目ごとのナレーション同期プロパティを持つ**（省略時は均等割りの
  早出しタイミングになり、語りより画面が先行してズレる）。ナレーションが項目ごとに順番へ
  話す構成では必ず指定する:
  - `bullets`: `appearAtSec: number[]`（bullets と同じ長さ。各項目の出現秒）
  - `vs`: `columnAtSec: [number, number]`（[left, right] の出現秒）
  - `flow`: `highlightAtSec: number[]`（steps と同じ長さ。各ステップの点灯開始秒）
  すべて `segStart(SEG, i)` で組む（例: `appearAtSec: [segStart(SEG, 1), segStart(SEG, 2)]`）。
  matrix・layers のハイライトは現状ページ内蔵の固定タイミングのみ（ナレーション同期は未対応）
- カスタムシーンで「1つの要素の中の一部だけを語りに合わせて強調」したい場合（例: 副題に並ぶ
  2つの用語をそれぞれの説明文の開始で色を変える）は `useProgress(segStart(SEG, i), 0.3)` +
  `interpolateColors` で組む（`src/videos/ipa_sg/sg-L3-human-deception.tsx` の `HighlightSpan`
  が実例。詳細は references/custom-scenes.md）
- 章の切り替えは spec の `transitionIn`: まとめ前は `"wipe"`（専用）、本編内の場面転換は `"wipe-light"`
  （自前でワイプを実装しない — parts/transition.tsx が正）

**画面テキストの分量上限**（超えそうなら削るのではなくページを分ける）:

| 場所 | 上限 |
|---|---|
| title | 2行・各行13文字 / keywords 3個・各7文字 |
| bullets | 3項目 / text 14文字 / sub 20文字 |
| vs.rows | 各列3行 / 左右で観点(k)を揃える |
| flow.steps | 3〜5個 / name 4文字 |
| quiz | question 20文字 / 選択肢 text 18文字 / correct は1つ（正解位置は A/B を混ぜる） |
| 字幕セグメント（全ページ） | 1文25〜45字・話し言葉（〜です・〜ます）。**字幕帯の1行は全角約30字が限界**で、超えると2行になり最後の1〜2字だけが2行目に落ちる。英数字混じりの文は全角換算で数えること（sg-L29 v3 で「JIS Q 27002という規格に並ぶ一つ一つの対策を、管理策といいます。」が折り返した）。言い回しを変えたら、その文が出るフレームを1枚見て確認する |

**カスタムシーンの決まり**（詳細とレシピは references/custom-scenes.md）:
- 本編ページは `<SlideShell narration={...}>` で包む（字幕と余白の保証）。幕間だけ例外
- 文字サイズは `videoType` か `モック値 × SCALE`（最小 9×SCALE=36px）
- 出現アニメーションは `useAppear` / `usePop` / `useFlyIn` / `useProgress` を時間差で
- 線・矢印の図解は `parts/draw.tsx` の `DrawPath` / `ArrowMarker`（SVGの手計算を減らす）
- アイコンは `<Ms name="..." />`。名前は `references/icons.md` のリストから
- クイズ的なページを自前設計する場合も、正誤は**色 + ○記号の二重符号化**（colors.correct 系）を守る

### 7. 全ページを静止画で目視確認(省略禁止)

```bash
node scripts/stills.mjs <id>
```

`stills/<id>/` の**全ファイルを Read で開いて見る**。チェック観点:

- はみ出し・折り返し・重なりがないか / アイコンが文字列のまま出ていないか
- 字幕帯に文が出ているか（telop の書き忘れ・narration の渡し忘れはここで見える。
  なお stills はシーン末尾なので、写るのは各ページ最後のセグメントの字幕）
- **単調でないか**: 並べて見て、同じ視覚文法が連続していたら設計(工程3)に戻る
- **0.5秒で伝わるか**: そのページのメッセージが一目で入ってくるか
- スカスカ/ぎゅうぎゅうのページはないか

とくに図解系のカスタム（グリッド・SVG座標もの）は、要素のあふれ・重なりが lint/tsc では
検出できず**静止画でしか見つからない**。ここで1回は直しが入る前提で時間を使う。
静止画で確認せずに完成報告するのは、このワークフロー最大の禁止事項。

**stills はシーン末尾しか写らない**ので、「出現前にゴミが見えている」「語りより画面が先行して
いる」系は stills では絶対に見つからない（矢じりの三角形・線の端点の残り・カウントアップの0が
実際にレビューで指摘された）。**時間で切り替わる要素があるページは、その要素が出る前の
フレームも1枚見る**:

```bash
npx remotion still <id> <出力>.png --frame=<フレーム番号> --scale=0.5
```

フレーム番号は `scripts/stills.mjs` が出す各シーンの秒数を積み上げて ×30fps。
出現前フレームで見るべきものは references/custom-scenes.md（矢印・数字ドンの各項）。

### 8. レンダリングして納品

出力ファイル名は `<app接頭辞>-L<レッスン番号>-v<バージョン>.mp4` の app-lesson-version 形式
（例 `ip-L1-v1.mp4`）。初回は `v1`、同じ動画を作り直すたびに `v2`, `v3`… と上げる
（既存ファイルは上書きしない）。

```bash
npx remotion render <id> draft/<app>/<出力名>.mp4   # 例: draft/ipa_ip/ip-L1-v1.mp4
ffprobe -v error -show_entries format=duration -of csv=p=0 draft/<app>/<出力名>.mp4   # 359秒以下を確認
ffprobe -v error -show_entries stream=codec_type -of csv draft/<app>/<出力名>.mp4     # audio ストリームがあること
```

成果物は必ず `draft/` へ。**359秒を超えていたら納品しない** — 原稿を削って該当音声だけ
再生成し（references/narration.md）、作り直す。

レンダリング中に `delayRender()` の未解決タイムアウト（`Loading font Material Symbols Rounded …
was called but not cleared after 28000ms`）で落ちることがある。アイコンフォントの読み込みが
既定タイムアウトに間に合わないだけの一過性の失敗なので、コードは直さず
`--timeout=120000 --concurrency=3` を足して**そのまま再実行する**（並列数を下げると1タブあたりの
負荷が減って読み込みが間に合う）。**複数本を続けて回すときは発生率が上がる**（`Ms.tsx` の
`loadFont` がモジュール先頭で走るため、前の実行の後片付けと重なる）。フラグ付きでも落ちたら
まず単体で再実行し、それでも落ちるなら `--concurrency=2` まで下げる — 実際にこれで通った
（2026-07-30 の4本連続再レンダリング）。同じフレームで繰り返し落ちるときだけシーン側を疑う。

**`--timeout` は「レンダリング全体の実時間」より大きくする**（フォント読み込みの待ち時間ではない）。
`Ms.tsx` の `loadFont` はモジュール先頭で走るので、その `delayRender` ハンドルは**タブの寿命 =
レンダリング全体の間ずっと生きている**。したがって `--timeout` を全体の所要時間より小さくすると、
フォント自体は読めていても**最終フレーム間際で必ず落ちる**。並列数を下げるほど所要時間は伸びるので、
`--concurrency=1` にするなら `--timeout=1200000`（20分）のように大きく取る
— `--concurrency=1 --timeout=300000` で5分の動画を回すと、8978フレーム中8903で
`not cleared after 298000ms` になった（2026-07-30 の sg-L25。`--timeout=1200000` で通った）。
並列数と timeout はセットで動かす。

**レンダリングは最後まで見届けてから報告を返す。** 5分の動画は `--concurrency=1` だと10分以上かかるので、
バックグラウンド実行にしたり監視を仕掛けたりしたくなるが、**そこで報告を返して終了してはいけない**。
あなたが終了してもレンダリングのプロセスは生き残るため、発注側は「動いているのか死んだのか」を
プロセス一覧から判定し、完了を待ち、あなたを再開させる羽目になる（2026-07-31 の第4章で3回発生）。
mp4 の生成・尺・audio ストリームを ffprobe で確認し、`QUEUE.md` を `👀 review` にするまで終了しない。

レンダリングできたら `QUEUE.md` の行を `👀 review` にし、成果物ファイル名と尺を埋める（工程0）。

**完了報告は短く固定する**（多数の動画を続けて作るとき、報告が長いと発注側の文脈が溢れる）:

- 動画ID / 出力ファイル名 / 尺（秒） / 原稿の総文字数
- 構成の一行要約（例: `title→導入2→本編7→幕間→クイズ3→まとめ`）
- 新規に作ったイラスト部品（ファイル名だけ・なければ省略）
- **人に見てほしい点・判断に迷った点（最大3つ）**
- 台帳を更新した行

各ページのメッセージとレイアウトは `narration/<app>/<id>.md` に書いてあるので、
**報告に展開しない**。原稿・tsx の中身も貼らない。

### 9. 指摘をスキルに還流する（省略禁止）

**この工程は、人の指摘を受けて動画を直したとき（工程0の `rework` 受注、または
「この動画のここを直して」という依頼）に必ず実行する。** 新規制作をしただけで
終わるときは対象外（まだ誰からも指摘されていない）。

動画は1本ごとに新しい文脈で作られ、その動画を作ったエージェントは指摘が出る頃には
もういない。**だから指摘は、直しを引き受けたあなたが書き戻さないと、この世から消える**。
次の1本を作るエージェントは同じ間違いを繰り返す。動画を直しただけでは仕事は半分。

指摘が**この動画固有でない**（＝次の動画でも同じ間違いが起きうる）と判断したら、
その場で書き戻す:

| 指摘の種類 | 書き戻す先 |
|---|---|
| 構成・分量・語りの方針 | `SKILL.md` の工程2・3 |
| ナレーション／音声の扱い | `references/narration.md` |
| カスタムシーンの組み方・レイアウト崩れの回避 | `references/custom-scenes.md` |
| 既製パターンの落とし穴 | `references/patterns.md` |
| 使ってよいアイコン | `references/icons.md` |
| その回の範囲の誤り（扱う／扱わないの切り分け） | `content_works/<app>/orders/<L番号>.md`（発注書） |
| 特定レッスン限定の事情（用語の主担当・依存関係） | `QUEUE.md` の該当行のメモ |
| 受注・状態・台帳の運用ルール | `QUEUE.md` の運用ルール節と `SKILL.md` 工程0（**両方**。片方だけ直さない） |

書き方は「次に読む人が同じ判断をできる形」で。**理由を1行添える**
（禁止事項だけ書くと、事情が変わったときに誰も直せない）。既存の記述と矛盾する場合は
追記でなく**書き換える**（矛盾した指示は残さない）。

**同じ内容が SKILL.md と references の両方に書かれている項目は、片方だけ直さない。**
正にする1箇所を決めて直し、もう片方はそこへの1行参照に置き換える
（コピーが残ると、次の人が古い方を読む）。

判断に迷ったら「これは今回の内容の話か、作り方の話か」で切る。作り方の話なら必ず還流する。
還流し終えたら、完了報告に**どのファイルの何を直したか1行**を足す。
