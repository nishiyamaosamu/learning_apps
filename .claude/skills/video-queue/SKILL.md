# 動画制作キューを回す（発注側）

あなたは**作る人ではなく、出す人**。動画1本の制作は、原稿1,300字・tsx 数百行・静止画12〜16枚を
読む仕事で、それをこの文脈でやると数本で溢れる。**1本 = 1サブエージェント（使い捨ての文脈）**にして、
戻ってくるのは十数行の報告だけ、という形を保つのがこのスキルの唯一の役目。

だから守ることは1つ: **自分で動画を作らない。** 原稿もコードも静止画も、あなたは見ない。

- 進捗の正: `content_works/video/QUEUE.md`（台帳）
- 制作手順の正: `create-learning-video` スキル（サブエージェントが使う）
- 範囲の正: `content_works/<app>/orders/<L番号>.md`（発注書）

## 手順

### 1. 台帳を読んで、出す本を決める

`content_works/video/QUEUE.md` を読む。受注の優先順位は台帳の運用ルールどおり
**↩️ `rework` → 🔨 `wip` → ⬜ `todo`**（直しと中断の引き継ぎが、新規制作より先）。
台帳の状態セルは**絵文字つきで書く**（⬜ `todo` / 🔨 `wip` / 👀 `review` / ↩️ `rework` /
✅ `done` / ⏸️ `hold`）。行を書き換えるときに絵文字を落とさない。

本数の指定がなければ **3本**を目安にする。指示があればそれに従う。

**出す前に止まる条件**（該当したら発注せず、ユーザーに何が起きているか伝えて指示を仰ぐ）:

| 条件 | なぜ止まるか |
|---|---|
| 次に出す回の**発注書が無い** | 範囲が未確定のまま作ると隣の回と重複する（下記） |
| 直前の発注が2本続けて失敗した | 環境側の問題（TTSの認証切れ・ディスク）が疑わしい |

**`review` が何本たまっていても止まらない**。レビューは人が好きなタイミングでまとめて消化するので、
溜まっていること自体は詰まりではない（本数だけ報告して、判断は人に任せる）。

### 2. 発注書の在庫を確認する

出す回に `content_works/<app>/orders/<L番号>.md` があるか見る。無ければ**発注せずに止まり**、
「第◯章の発注書がまだありません。先に起こしますか？」と聞く。

起こす場合は `content_works/ipa_sg/orders/README.md` の手順に従い、**章単位でまとめて**作る
（1本ずつ作ると隣との重複が見えない）。これは範囲を切る仕事なので、あなたがやってもよいし、
サブエージェント1体にその章ぶんをまとめて任せてもよい。1本の制作より軽い。

### 3. 1本ずつサブエージェントに発注する

**既定は直列（1本ずつ）。急ぐときでも同時2本まで。**

理由は工程ごとに詰まる場所が違うこと。シナリオと実装はLLM待ちなので並べるほど得だが、
**stills とレンダリングはヘッドレスChromeがCPUのおよそ半分を持っていく**（Remotion は既定で
コア数の半分を並列レンダリングに使う）。だから2本でマシンは埋まり、3本目からは奪い合って
**直列より遅くなる**。メモリも 1920×1080 のワーカーが並ぶぶんだけ食う。

2本出すなら**同時に出さない**。1本目がシナリオ〜実装に入ってから2本目を出すと、CPUの山が
ずれて一番効く。並列で出すときは、各エージェントが受注時に台帳へ `wip` を書き込むので、
**同じ回を2体に出さない**ことだけ確認する。

TTS のレート制限も並列時の未知数なので、音声生成でエラーが続くようなら本数を落とす。

**`--timeout=1200000` は本数に関係なく必ず発注プロンプトに書く**（下のテンプレ参照）。
`Ms.tsx` の `loadFont` の `delayRender` ハンドルはフォント読み込みが終わっても解放されず、
タブの寿命＝レンダリング全体の間生きている。つまり timeout は「フォント待ちの猶予」ではなく
**レンダリングが終わるまでの猶予**で、5分の動画に既定値や `--timeout=300000`（5分）を渡すと
終盤のフレームで必ず落ちる（L25 で 8978フレーム中8903で2回落ちて判明）。

これを書かずに投げると、エージェントは原因を内容側に探しに行くか、同じコマンドを何度も
再実行して時間を溶かす（実測: L19 が2回・L20 が2回・L25 が2回失敗した）。**内容の問題ではないので、
最初からフラグで避ける**。並列で出すときは、CPUの奪い合いを避けるため `--concurrency=1` も足す
（こちらは並列時だけでよい。ただし1本あたりの実時間は伸びるので、timeout を下げてはいけない）。

**発注するサブエージェントのモデルは必ず `opus` を指定する**（Agent ツールの `model` に
`"opus"` を渡す）。制作はシナリオ設計・1ページごとのレイアウト設計・静止画の目視判断と、
判断の密度が高い仕事で、ここを軽いモデルに落とすと「型に流し込んだだけ」の動画が上がってくる。
モデルを省略すると発注側のモデルを引き継ぐので、明示すること。

発注プロンプトはこの形を保つ。余計な指示を足さない（作り方はスキル側が持っている）:

```
content_works/video/QUEUE.md の <L番号>（<タイトル>）を担当して、学習動画を1本作ってください。
create-learning-video スキルを Skill ツールで呼び、工程0から工程8まで通してください。

- 発注書: content_works/<app>/orders/<L番号>.md
- 台帳（QUEUE.md）の更新はあなたの仕事です（着手で 🔨 wip、レンダリング完了で 👀 review。絵文字つきで書く）
- 完了報告は工程8のフォーマットだけ返してください。原稿・コード・静止画の中身は貼らないこと
- レンダリングは `--timeout=1200000` を必ず付けて実行してください（`loadFont` の `delayRender`
  ハンドルはレンダリング全体の間生きているので、`--timeout` はフォント待ちの猶予ではなく
  **総レンダリング時間**より大きく取る必要があります。既定値や 300000 だと5分の動画は終盤で
  必ず落ちます。内容側の問題ではないので、落ちても原稿やコードを疑わないこと）
- （並列で出すときだけ）いま別のエージェントも並行してレンダリングしています。上に加えて
  `--concurrency=1` も付けてください
```

`rework`（差し戻し）を出すときは、台帳のメモにある**指摘をそのまま貼り足す**。指摘は会話ではなく
台帳に書かれているのが正で、それを渡さないと同じものが上がってくる:

```
（上記に加えて）
この回は review で差し戻されています。台帳のメモにある指摘は次のとおりです:
<メモの指摘をそのまま>
直したうえで、工程9に従って「次の動画でも起きる指摘」はスキルへ書き戻してください。
```

### 4. 報告を受け取る

返ってくるのは工程8のフォーマット（動画ID・出力ファイル・尺・文字数・構成の一行・
人に見てほしい点・台帳の更新行）。

**長い報告が返ってきたら、そのまま転記しない。** 上のフォーマットに畳んでからユーザーに伝える
（畳まずに流すと、サブエージェントに分けた意味がなくなる）。同時に、報告が長かったこと自体が
`create-learning-video` の工程8が効いていないサインなので、ユーザーに一言添える。

失敗・中断の報告なら、台帳がその回を `wip` のままにして再開地点をメモしているはずなので、
それを確認して次に進む。**同じ回をその場で作り直させない**（同じ理由で失敗する）。

**エージェントがAPIエラーで即死したときはメモが無い**（書く前に落ちるので、鉄則が守られない）。
このときは**発注側が代わりに再開地点を書く**。書かないと、次に拾う側が工程0からディスクを
探り直すか、最悪もう一度作り直す。再開時の発注プロンプトには「原稿やコードを作り直さないこと」を
必ず添える（無いと、揃っている成果物を上から作り直しにいく）。

ディスクから進捗を判定するときの注意: **音声の有無は `narration/<app>/<id>.jobs.json` の名前から
`public/audio/<app>/<id>/` を数える**。`src/videos/<app>/<id>.tsx` の名前から辿ると、tsx がまだ
無い段階（＝音声はあるのに実装前）で「音声0本」と誤判定する。実際にこれで L27 を
「音声生成から」と誤って書き、受注側の工程0が46本あることを見つけて訂正している。
判定を誤っても受注側が直せるが、**メモは「ここから」ではなく「ここまでは在る」を書くほうが安全**。

### 5. ひと回し終えたら、人に渡す

まとめて報告する。ユーザーがやるのはmp4を見ることだけなので、見る対象と判断の入れ方を書く:

```
今回できたもの:
- SG-L5 ランサムウェアとボットネット → draft/ipa_sg/sg-L5-v1.mp4（4分52秒）
- SG-L6 攻撃者と不正のメカニズム → draft/ipa_sg/sg-L6-v1.mp4（4分31秒）

見て良ければ「L5 review ok」と言ってください（アプリへ公開して ✅ done にします）。
直しが要るなら ↩️ rework にしてメモに指摘を書きます（「rework にしといて、まとめが弱い」でOK）。
残り: ⬜ todo 85本 / 👀 review 3本
```

### 6. 「review ok」と言われたら、アプリへ公開する

レビューが通った回は draft に置いたままにせず、アプリの完成品置き場
（`apps/<app>/contents/videos/`）へ**移す**。**手でコピーしない**。1コマンドで
mp4のコピー・`base.json` への登録（尺は ffprobe の実測）・台帳を ✅ done にする・
draft から消すまで揃う:

```bash
cd content_works/video
node scripts/publish.mjs sg-L1          # 複数まとめてもよい（sg-L1 sg-L2）
node scripts/publish.mjs --prune        # 昔に公開した回の draft が残っていたら掃除
```

- アプリ側の動画ID = **L番号**（`L1` → `contents/videos/L1.mp4`）。視聴進捗のキーなので後から変えない
- 章（`VideoChapter`）は QUEUE.md の `### 第N章 …` 見出しから採る。見出しが無いアプリ（ipa_ip）は
  `--chapter <id>:<タイトル>` で明示する
- 視聴後の確認クイズ（`VideoItem.quizzes`）は**入れない**（クイズは動画の中にある。二度出さない）
- 公開したmp4はgit対象外（`apps/*/contents/videos/*.mp4`）。追うのは `base.json` の登録だけ
- 公開すると **その回の draft は消える**（公開した版も旧版 `-v1`… も）。`draft/` はレビュー待ちだけを
  置く場所なので、`ls draft/<app>/` に残っているものが「人がまだ見ていないもの」と一致する。
  台帳の ✅ done 行の「成果物(draft)」欄は、どの版を公開したかの記録（ファイルはもう無い）
- 初回のアプリだけ `apps/<app>/pubspec.yaml` の `flutter.assets` に `- contents/videos/` を足す

## やらないこと

- **自分で動画を作らない**（原稿を書く・tsxを触る・stillsを開く、はすべてサブエージェント側の仕事）
- **`done` を付けない**。完成の判断は人がする。人が口頭で承認したときは、手で `done` と書くのではなく
  `scripts/publish.mjs` を走らせる（公開とセットで初めて `done`）
- 台帳の表以外の場所に長文を書かない（詳細は `narration/<app>/<id>.md` にある）
- サブエージェントの報告を鵜呑みにしない。尺が359秒を超えている・成果物ファイル名が
  台帳と食い違うなど、**報告の中で矛盾している点があれば人に伝える**

## 進捗を聞かれたとき

台帳を数えて答える。状態ごとの本数と、`review`（人待ち）・`wip`（中断）に何があるかを挙げる。
`wip` が増えていたらそれは詰まりのサインなので、そう伝える。
